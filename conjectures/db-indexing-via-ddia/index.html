DB Indexing via DDIA

June 11, 2026

Here's a breakdown of hash indexes, as explained by Kleppmann in Designing Data-Intensive Applications, and how your databases store information to allow for data retrieval.

The core example layed out is that suppose you have a database that's a file you keep appending to, where every write adds a new line. This is obviously a simple operation, but how do we find anything fast?

One solution is to keep an in-memory hash map where every key is an actual data key (e.g., 12345) and every value is the byte offset in the file where that record lives. This allows us to scan the database for what we need, putting us in the correct spot every time. Whenever we write a new record to the DB, the hash map is updated with the new byte offset. On read, we look up the key in the hash map, get the offset, gp to that position, and read the value—all in one disk seek.

The immediate issue that comes up is how we can only ever append, resulting in the file growing forever. The fix is compaction: periodically merging segments and throwing away duplicate keys, keeping the only recent value for each. This happens in a background thread, letting us read and write to the database uninterrupted. Even with that, all keys must fit within RAM (since the hash map lives in-memory) and if there are too many distinct keys, everything breaks down.
