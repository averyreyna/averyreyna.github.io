Legible Software with Categorical Structure

May 11, 2026

Software is legible when you can reason about the whole from its parts' interfaces alone — without opening any of them. Most codebases fail this. Internals leak outward. Knowledge of how something works becomes load-bearing for anyone trying to use it. What starts as a clean separation collapses into a single thing you have to understand all at once.

Category theory has a reputation for being maximally abstract. But its core move is exactly the formal version of what legibility requires: objects are opaque. All you know about them is what morphisms go in and out. Composition is by signature, not by inspection. If A's output type matches C's input type, you can wire them together without knowing what either one does internally. That's the whole apparatus.

I want to work through what this looks like in practice using a concrete comparison — authentication — and a concept-based architecture that takes the categorical constraint seriously as an engineering principle.

The failure mode

Here is a conventional approach: an Express app with Prisma, handling user registration and login.

// routes/auth.ts
router.post('/register', async (req, res) => {
  const { email, password } = req.body;

  const salt = await bcrypt.genSalt(10);
  const hashedPassword = await bcrypt.hash(password, salt);

  const user = await prisma.user.create({
    data: { email, password: hashedPassword, salt }
  });

  res.json({ user });
});

router.post('/login', async (req, res) => {
  const { email, password } = req.body;

  const user = await prisma.user.findUnique({ where: { email } });
  const valid = await bcrypt.compare(password, user.password);

  if (!valid) return res.status(401).json({ error: 'Invalid password' });
  res.json({ user });
});

Three things have gone wrong. The password hashing logic appears in two places — nothing prevents a third. The password and salt columns live on the User table, so authentication is already entangled at the schema level. And each route handler knows about bcrypt directly, collapsing business logic, HTTP handling, and persistence into the same function. To work on any part of this, you have to understand all of it.

The categorical structure

A concept-based architecture treats each concern as an independent state machine: its own state, its own actions, no shared references with anything else. The only way into a concept's state is through its actions. Here is the same password logic written as a concept.

// concepts/Password.ts
const PasswordConcept: Concept = {
  state: {
    passwords: new Map<string, { hash: string; salt: string }>()
  },

  async execute(action, input) {
    switch (action) {

      case 'set': {
        const { user, password } = input;
        const salt = await bcrypt.genSalt(10);
        const hash = await bcrypt.hash(password, salt);
        this.state.passwords.set(user, { hash, salt });
        return { user };
      }

      case 'check': {
        const { user, password } = input;
        const stored = this.state.passwords.get(user);
        if (!stored) return { error: 'User not found' };
        const valid = await bcrypt.compare(password, stored.hash);
        return { valid };
      }

    }
  }
};

Password.set is the only door into that state. Aliasing across concept boundaries is structurally impossible, not just a convention. The decision to wire password creation to user registration — which in the traditional approach lives inside the route handler — is now a separate, named rule.

const registrationSync: SyncRule = {
  name: 'NewPassword',
  when: [{ concept: 'User', action: 'register', outputPattern: { user: '?user' } }],
  then: [{ concept: 'Password', action: 'set', input: { user: '?user', password: '?password' } }]
};

The person writing this sync never opened User or Password. The output of User/register includes a user field. The input of Password/set accepts a user field. The types line up, so you compose. That is the categorical move made concrete.

What you gain

Legibility is the obvious payoff — you can read a concept by reading its actions, and you can read the system by reading its syncs. But the structural consequences go further.

Adding a feature means adding a concept file and a sync rule, nothing else. No changes to existing concepts. No risk of breaking the registration flow by touching it. The new behavior wires in from the outside, the same way the original behavior was wired in.

Every action invocation is a record. The full execution trace of any request — every concept touched, every input and output, in order — is a path in a diagram you can query. Debugging stops being about reconstructing what happened from logs and starts being about reading what was recorded.

The conjecture

Software is most legible when its composition structure is categorical: each piece exposes a signature, composition is by signature alone, and nothing requires inspecting internals to use correctly. Category theory doesn't make code abstract — it formalizes the conditions under which code stays readable as it grows.
