A Type That Shows Its Work

June 23, 2026

I've been building a small editor called Chaperone. It's a Pandas notebook, but it watches the data you load and works out a rich type for every column before you've run anything. Not just “this column is text” but “this is an email address,” “this is a US dollar amount that's never negative,” “this is a primary key.” Then it uses those types to catch mistakes as you type: try to .sum() a column of email addresses and you get a red squiggle, because the type it inferred from your actual rows says that column isn't a number.

That's the pitch, and it's not what this post is about. This post is about a much smaller thing: the little panel that opens when you click on one of those inferred types and ask how?

Because here's the problem with a tool that infers things and then judges you on them. The moment it decides order_id is a key and uses that decision to rank your autocomplete, or decides amount_usd is a currency and warns you about a negative value, it has set itself up as an authority. And an authority you can't interrogate is one you'll eventually stop trusting. The first time it's confidently wrong, and it will be, you need to be able to lean in and say: show me why you think that. Not a plausible-sounding story. The actual reason.

The cascade

Inference in chaperone is deliberately dumb, in the good way. It's a cascade of detectors, run most-specific-first[1]: 

Key → Currency → Email → Date → Bool → Int → Float → Categorical → string

Each detector looks at every non-blank value in the column and either accepts the whole column or rejects it. The first one that accepts wins. string sits at the bottom as the always-true fallback. If nothing else matches, it's free text.

The detectors are exactly as literal as they sound. Key demands that every value be a whole number, that they're all distinct, and that they strictly increase. Email demands that every value match an email pattern. Categorical wants a handful of distinct values that actually repeat. Currency is the interesting one. It won't even look at the numbers unless the column name matches something like amount|price|cost|revenue|total|usd. Hold onto that name-match.[2]

So for a column called order_id full of 1001, 1002, 1003…, the cascade tries Key first, finds the values unique and increasing, and stops. Type: Key[int]. Done. The other seven detectors never run. That “stops” is the whole story of this post.

What inference forgets

The function that does the real work is called inferColumn, and it is ruthless about throwing things away. It walks the cascade, and the instant a detector accepts, it grabs the winning type and returns. Everything else evaporates: which detectors it tried, why each one said no, which specific cell broke which rule. None of that survives. inferColumn keeps exactly one thing: the answer. That's all the editor needs to draw a squiggle.

But the discarded stuff is precisely what you want when you ask “how?” When the editor types order_id as a plain Int instead of the Key you expected, the useful information isn't “it's an Int.” It's: Key was tried, and Key was rejected, because row 7 repeats the value in row 3, so a key it cannot be. That's the sentence you came for. And inferColumn deleted it microseconds after computing it.

The explanatory twin

So there's a second function, traceColumn, and the only thing that makes it interesting is what it doesn't do differently.

It walks the same cascade. The same list of detectors, in the same order, applying the same predicates to the same values. The one difference is that it writes everything down. For each detector it records a verdict (winner, rejected, or not-reached) and the supporting detail. For the winner, the evidence (“unique, non-null, strictly increasing”). For each rejection, the reason (“values repeat, so it can't be a key”). For the detectors after the winner, nothing: they were never reached, and the trace says so honestly rather than pretending they were considered.

Click a type in chaperone's dataset view and you get this: 

how amount_usd was typed
  ✗  Key           "12.50" isn't an integer
  ✓  Currency      name reads as USD · all numeric · none negative
  ·  Email · Date · Bool · Int · Float · Categorical — not reached
  ∅  nullable      2 blank cells
  #  cardinality   11 distinct of 12

You can read the entire decision off the panel. Key was tried and lost on the first value that wasn't a whole number. Currency was tried and won. Five detectors never ran. And underneath, two plain facts about the column: it has two blank cells, so it's nullable; it has eleven distinct values across twelve rows.

Now, here is the part I actually care about. inferColumn and traceColumn don't have separate ideas about how typing works. They read from the same list of detectors: one array, defined once, that both functions iterate. inferColumn reads only the verdict (“did this one accept?”). traceColumn reads the verdict and the reasoning (“…and here's why”). Same walk, two readers, differing only in how much each one bothers to record.

Which means the explanation cannot drift from the decision. There's nothing for them to disagree about. The trace isn't a model of the inference, or a reconstruction of it, or a story told after the fact about what probably happened. It is the inference, with the receipts kept. If you ever changed how Key works, both the typing and its explanation would change together, because they're the same detector. You couldn't make them disagree if you tried.

Down to the cell

A faithful account of the reasoning is good. But “values repeat” still points at an abstraction. The trace goes one step further and points at the data.

Every rung in that panel remembers which sample cells it's talking about. Hover the winning Currency row and the cells that justify it glow gold in the table below. Hover a rejection and the single cell that broke the rule glows red: the "12.50" that disqualified amount_usd from being a key, or the duplicate that knocked order_id down from Key to Int. Hover the nullable fact and the blank cells light up.

That's the loop closed. You start from an abstract judgment, this column is a currency, and you can walk it all the way back, by hand, to the literal cells that forced it. It's the difference between a tool saying “trust me” and a tool saying “look.”

Why faithfulness is the whole game

Most explanation features in data and ML tooling are generated separately from the thing they explain. The faithfulness problem.[3] A model makes a prediction; a second system produces a chart, or lately an LLM is asked to narrate why the first system did what it did. These can be illuminating. They can also be confidently, fluently wrong: a plausible rationalization that has come unstuck from the actual computation, and you have no easy way to tell which one you're looking at.

Chaperone's trace can be incomplete (it only shows the detector cascade, not every nuance), but it cannot be unfaithful, because it isn't a separate account at all. It's the same code path, run with a notepad.

And notice what that buys: the trace doesn't flatter the system. Look back at the Currency line. It says “name reads as USD.” That's the trace admitting, out loud, that the currency detector leaned on the column's name, not purely on its values. That's a genuine soft spot in the inference. A separately-authored explanation would be tempted to paper over that. A faithful one can't, because the name-check really is part of the decision, so it really is part of the trace. The explanation is honest about the system's weaknesses for the same structural reason it's honest about everything else.

This matters more the further your types drift from things you declared. When you write int in a type annotation, the justification is right there. You wrote it. But chaperone's types come from data you didn't author and may never have read closely. The justification lives in cells you've never looked at. The trace is how you get it back.

The panel is small. It's a cold path[4]: it only runs when you click, because nobody needs it until they doubt something. But it's the part that keeps the inference legible, and legibility is the whole bargain. A type system that judges you owes you an answer when you ask why. This one keeps the receipt.

[1] Order is the trick: every key is also an int, and every int is also a float. Listing the detectors specific-to-general means the first acceptance is automatically the tightest type that fits. ↩

[2] This name-match is the weakest link in the cascade: a column of perfectly good dollar amounts called qty would never be tried as currency at all. I'd rather recover currency from the values themselves (symbols, decimal places, ISO codes sitting in the data), but that's its own rabbit hole. For now the honest move is to let the trace admit the dependency out loud rather than bury it. ↩

[3] This is the faithfulness problem in interpretability: an explanation can be perfectly plausible and still be a story told after the fact rather than an account of what the system actually did. A saliency map claiming “the model looked here” is a separate computation from the prediction, and the two can quietly disagree. Chaperone sidesteps the whole question by refusing to make the explanation a separate computation. ↩

[4] traceColumn runs only when you click a type. You never need the argument until you doubt the conclusion. The fast path that draws squiggles never pays for it. ↩
