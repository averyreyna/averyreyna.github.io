More on Motivation

I have felt a too-muchness when diving into fields like formal methods or program synthesis, subjects that are anachronistic in their applications and learnings. You can ask questions about user interfaces and stretch their concepts to the actual syntax itself (the brackets, the keywords, the symbols) to gauge where we can decrease the bottleneck in our gulf of execution as code writers. It's funny to think about how I got to this field by way of AI-assisted coding, fully obsessed with structured knowledge transfer between developer eyes and programming agents. I think I'm just fond of correctness and verification. While this quote from Flusser's Gestures (a collection of essays that ask heady questions like "Does writing have a future?") is a little too cynical for my taste, the gist of the excerpt still rings true. Every discipline feels like it's some applied version of the one below, abstracting more details in order to observe relationships between concepts more clearly.

The so-called humanities appear to be working on such a theory. But are they? They work under the influence of the natural sciences, and so they give us better and more complete causal explanations. Of course, these explanations are not and perhaps never will be as rigorous as those in physics or chemistry, but that is not what makes them unsatisfactory.

Notes from Making Abstraction Concrete

  • Dijkstra points out that the point of abstraction is to create a new semantic level in which one can be absolutely precise in depicting a phenomenon
  • AI research explores invoking the abstraction process in LLMs to define higher-level, reusable modules for managing complexity in domains such as system design
  • Abstraction is widely used in interactive systems, typically through GUIs guiding the user between levels of abstraction in order to get a feel for the entire system
  • Min et al. make a deliberate deemphasis of common associations with "higher-levelness" and/or simplicity; this is due in part to relativity: a user's conceptual interests shape what they deem as "easy" or familiar; this distinction is important because it is difficult to disentangle the process of abstraction from notions of generalization
  • More on that: this connects with the evolution of programming languages: is Python really "high-level" from a conceptual standpoint? I understand it's a ways away from being something more procedural, actually manipulating memory allocation. However, maybe it's something closer to opacity: the syntactic capabilities of a language make engineering tasks more/less abstract, with differing languages being good at different things (duh!)
  • Abstraction designs do not influence only a single stage of Norman's seven stages of action—they shape all stages—suggesting that introducing an orthogonal dimension of abstraction across the Gulfs may reveal richer patterns of how these designs influence interaction
  • A user's mental model and the system can span the gulf of abstraction not only by shifting to higher/lower levels, but by moving through a space
  • Random thought: can this be applied to actual programming language text? re: Slim Lim's thoughts on concrete syntax; only up until very recently, the only way to actually develop meaningful, substantial software was to manipulate code; sure, we have direct manipulation programs with robust type checkers to make writing code easier, but that still required at least some technical savviness—would a regular software dev be able to reason with those programs effectively? I guess I'm trying to get at the fact that we're realizing software engineering is not only about coding, and that rings true outside of an agile workplace; back to this opacity analogy: through natural language, now, you can be an expert in system design, and even if you're not technically literate or working on something outside of your scope, you're now able to "abstract" away code and focus on its interactions; and I mean "abstract" in the schema way, not the simplification way.
  • The emergence of LLMs has enabled ways to significantly reduce the costs involved in the sensemaking stages

Why PL + HCI?

I think it's because I am drawn to the specificity of language—including the acute semantics of programming.

That one Solar-Lezama quote sums up some of my feelings:

Code presents unique challenges that derive from the extreme precision required to write correct programs — a few characters can be the difference between a correct program and one that contains a dangerous vulnerability. But code also presents unique opportunities; unlike other tasks for which LLMs have shown promise, code benefits from precise semantics, which allow us to test it and to reason formally about its behavior.

Code is its own interface and through things like type systems, you make the process of translating abstract ideas for programs into a reality. I want to create a language with heuristics that are intuitive.
