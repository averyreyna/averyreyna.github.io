Typed Holes and Gradual Consistency

An incomplete program usually means there is no program at all: the compiler refuses it and you get nothing back. A typed hole takes a different view, treating a missing piece as a known gap that the type system can still reason about, so the rest of the program keeps its meaning while a piece is absent. The hole has an expected type, and the editor can say what belongs there before you fill it. Reading through how Hazel's statics layer implements this, a few ideas do most of the work.

The Gradual Unknown

Gradual typing adds an unknown type ? that is consistent with every other type. The useful detail is that the unknown carries provenance, a record of where it came from: an empty hole, a position where a type is still being synthesized, or a tolerant default. Because the unknown remembers its origin, a later conflict can be localized to the node responsible instead of failing the whole program at once.

One Expected-Type Field, Not Two Modes

The textbook presentation splits typing into synthesis, reading a type off an expression, and analysis, checking an expression against an expected type. In practice you do not need a two-case mode for this. You can thread a single expected-type field down the tree walk and let "no expectation" be the unknown sentinel. If the parental expectation is ?, the node is in synthesis; otherwise it is being analyzed against that type. One field carried through one walk.

Consistency Is a Lattice Meet

The gradual-typing relation ~ asks whether two types can agree, and it turns out to be a partial meet on the type lattice. You take the greatest lower bound ∧ of the expected type and the synthesized type. If it exists, that is the resolved type. If it does not, that absence is the error itself, so the red squiggle is not a separate check but the case where the meet returns nothing.

Gradual consistency is a partial meet on the type lattice, and the type error is meet-failure.

Tolerant Elimination

Each operator that takes a type apart, such as "this should be a function, so hand me its domain and codomain," is a small matched judgment: normalize the type, pattern-match on it, and on the unknown propagate the unknown rather than giving up. Every rule has a tolerant variant that defaults to an internal ?, so even a broken program still yields a type at every node and the walk never crashes.

Notes

The result is that the question of what type can go here is not a separate analysis bolted onto the editor, but a field read off a single tree walk. The program is walked once against the context Γ, and each node carries a bundle: the context in scope, the expected type, the synthesized type, the resolved type after the meet, the error marks, and the ranked list of completions valid at that position. The cursor inspector is a lookup into that bundle.

This sits on top of the lambda calculus and the broader type-theory thread, and the consistency machinery is ordinary lattice theory. The remaining question is where the expected type at a hole comes from, which is the subject of schema inferred from live data.
