The Elm Architecture

The Elm Architecture emerges naturally from the language, but the pattern is useful for any frontend project. Redux takes direct inspiration from it. Every Elm program breaks into three parts:

  • Model: the state of your application
  • View: a way to turn your state into HTML
  • Update: a way to update your state based on messages

The program produces HTML to show on screen, and the browser sends back messages of what is going on ("they clicked a button!"). Elm renders the initial value, then enters a loop: wait for user input, send a message to update, produce a new Model, call view to get new HTML, show it, repeat.

The Canonical Counter

-- MODEL
type alias Model = Int

init : Model
init = 0

-- UPDATE
type Msg = Increment | Decrement

update : Msg -> Model -> Model
update msg model =
  case msg of
    Increment -> model + 1
    Decrement -> model - 1

-- VIEW
view : Model -> Html Msg
view model =
  div []
    [ button [ onClick Decrement ] [ text "-" ]
    , div [] [ text (String.fromInt model) ]
    , button [ onClick Increment ] [ text "+" ]
    ]

The point of the model is to capture all the details of the application as data. For a counter, that is just an Int. Each onClick handler says: when someone clicks, generate a message. The update function describes what to do when each message arrives.

Growing the Model

A text-reversal app tracks the field's content in a record. A plain String would work, but records scale better as fields accumulate:

type alias Model =
  { content : String }

type Msg
  = Change String

update msg model =
  case msg of
    Change newContent ->
      { model | content = newContent }

Every keypress triggers a Change message and a fresh render. The state must be tracked explicitly in the model. Otherwise there is no way for view to show the reversed text.

A form with name, password, and password-confirmation fields is the same shape with three fields and three message variants, plus a viewValidation helper that compares the two passwords. Since input and div are just normal Elm functions taking a list of attributes and a list of children, repetitive view code refactors into helper functions like any other code.

Notes

The advice that stuck with me: start with a minimal model, maybe one field, and let the needs of update and view pull more structure in. The architecture is a fixed skeleton, so all design effort goes into choosing the right data, which is the right place for it.
