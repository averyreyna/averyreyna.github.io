State, Formally

In PL theory, state is any information that persists and can change over time during a computation. A variable holding a value is state; a memory address containing a number is state. The fact that something can change is what makes it state, as opposed to a pure value, which is fixed.

State Machines

The mathematical model underlying most of PL theory's treatment of state is the state machine: a set of possible states, a set of actions or transitions that move you between them, and an initial state. When the WYSIWID paper says a concept is "defined as its own state machine," it means the concept has a set of possible configurations its data could be in, and actions are the only thing that transitions between them, a very classical formalization.

state: {
  users: new Map([
    ['uuid-123', { name: 'alice', email: 'alice@example.com' }],
    ['uuid-456', { name: 'bob',   email: 'bob@example.com'   }],
  ])
}
Think of each concept like a tiny database that only accepts writes through a strict API. The Password concept's state is essentially a table of hashed passwords. The only way to write to it is through Password.set. The only way to read from it (directly) is through Password.check. No other concept can reach in and touch it. That's the whole independence guarantee.

Stateful vs. Stateless

  • Stateful computation, where the result can depend on history, not just current inputs: calling register("alice") twice gives a different result the second time
  • Stateless / pure computation, where the same inputs always give the same outputs and nothing is remembered

Most real programs mix both, which is where a lot of complexity comes from. In the lambda calculus, pure computation has no state at all; you substitute expressions for variables and reduce. State had to be added on top, and adding it cleanly is genuinely hard; it gave rise to monads in Haskell (threading state through pure functions), effect systems (type-level tracking of which functions may have effects), and linear types (state used exactly once, preventing aliasing bugs).

Aliasing and Concept Boundaries

The thorniest thing state introduces is aliasing, two names pointing at the same piece of state, so changing it through one unexpectedly changes it through the other. This is why the paper is so strict about concepts never sharing state or referencing each other's internals: aliasing across concept boundaries would break the independence guarantee completely.

Notes

The paper takes a classical position: concepts as state machines, explicit transitions, no state leaking across boundaries. This is the discipline formal-methods people like Daniel Jackson (who built Alloy) have advocated for decades. The new part is applying it to LLM-assisted development and asking what software structure makes generated code more reliable. Whether state lives in RDF triples or a plain Map is mechanism, not concept.
