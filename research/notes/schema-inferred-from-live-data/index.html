Schema Inferred from Live Data

Typed holes need an expected type at the cursor. The usual source of that type is a declaration: you wrote a signature, and the editor reads it back. A more interesting source is the data itself. If a program is a chain of operations over a table, the expected type at a hole can be inferred from the live data flowing to that point, so the type is the runtime schema at that stage of the pipeline. The feedback is the same kind of expectation at the cursor, but it works in plain text with no declarations and stays grounded in the actual data.

Rich Types from a Sample

The worry with inferring types from data is that you only recover ints and bools. Sampling the actual rows recovers much more. A unique, non-null, monotonic column reads as a key; a column whose values all match an email pattern reads as an email; a non-negative float reads as a currency; and a column with only a few distinct values reads as a categorical. Nullability, cardinality, and ranges come along too. That richness is what makes feedback at the hole worth having:

column         | inferred type           | why
---------------|-------------------------|-----------------------------------
order_id       | Key[int]                | unique, non-null, monotonic
customer_email | Email                   | every value matches an email pattern
order_date     | Date                    | parses as ISO dates
amount_usd     | Currency[USD] (>= 0)    | float, non-null, never negative
region         | Categorical{NA,EU,APAC} | few distinct values, low cardinality
is_refunded    | Bool                    | true / false

Ranked by What the Operation Means

Once the columns carry rich types, completion can rank candidates by what the operation means rather than alphabetically. Grouping by a categorical or a date makes sense, while grouping by a unique key does not, since every group would hold a single row. A sum wants a numeric column, so an email column can be flagged before anything runs.

The Error You Would Otherwise Never See

Typing a non-numeric column into a sum draws a squiggle at the cursor. In plain pandas that same code runs: it concatenates every string in each group into one long value and quietly returns garbage. Because the expected type came from the data, the editor can catch the mistake before execution.

Why "Live" Is the Point

Everything above could be faked with a declared schema. The part that cannot be faked is that the expectation came from the data, so changing the data changes the expectation. Swap the source file and a category that is no longer present drops out of the ranking; a column that now has blanks becomes nullable, and the sum warns that it will skip those nulls. The code is untouched in both cases, and the feedback moved because the data moved. A declared schema is frozen, while an inferred one tracks whatever is actually there.

Notes

This depends on the hole machinery from typed holes and gradual consistency for the expectation, and it sets up the dynamic side, where the partial program runs and the result fills in as you type: value liveness and hole closures.
