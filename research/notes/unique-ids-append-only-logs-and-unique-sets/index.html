Unique IDs, Append-Only Logs, and Unique Sets

The first semantic technique the survey reaches for, and the one that makes translated operations context-independent, is the unique id. Instead of referring to a piece of content by a mutable descriptor like its index, you assign it an immutable unique id (UID) at creation and use that id in every operation that touches it.

By "piece" I mean anything the view treats as a distinct thing with its own long-lived identity — a row, a list element, a cell — even though that piece is internally mutable. A UID is the distributed version of a pointer to such an object, and it plays the role of a primary key the way one would in a relational database. The idea is useful even outside collaboration; spreadsheet cells already want stable identities. For all replicas to agree on a piece's UID, the content's creator assigns the id at creation time and broadcasts it, and the id must stay unique even when several users create content concurrently.

Append-Only Log

An append-only log records events indefinitely. As a CRDT it has a single operation, add(x), where x is an immutable value stored alongside the event. Translation turns add(x) into cadd(id, x), attaching a fresh UID so that two events carrying the same value remain distinguishable. Given a history of such operations, the current state is simply the set of all (id, x) pairs.

A log is unordered, just like a set, so if you want a reading order you fold a logical timestamp into the value and sort by it. A logical timestamp is compatible with the causal order ≺, so this ordering never contradicts causality.

Unique Set

A unique set is an append-only log that also allows deletion, which makes it the basis for any collection that grows and shrinks dynamically. Its two operations are the distributed versions of new and free running on every node:

  • add(x) — same behavior as the log, minting a UID and storing an (id, x) pair
  • delete(id) — where id is the UID of the element to remove

With UIDs acting as distributed pointers, the unique set behaves like a database table whose rows you insert and delete by primary key. The new/free analogy is literal: this is the C/C++ picture of allocating a chunk of memory and reaching its contents through a pointer, lifted to a setting where every node runs the allocator. Deletion only behaves under causal-order delivery — if delete(id) causally depends on the add that created id, the add is guaranteed to arrive first everywhere, so there is always something there to free.

Delegating the Causal Order

Worth being precise about where that guarantee comes from: the unique set does not assume causal order on its own, it delegates that responsibility to whatever network messaging infrastructure carries the operations around. The contract is conditional — "if your delivery layer is causal-order, then this works correctly." It is the familiar distributed-systems move of decomposing the problem and letting each layer own its own concern, rather than trying to solve everything in one place.

Notes

What I want to keep is how much weight rests on identity. Once every piece of content has a stable UID, the hard collaborative operations — delete, move, re-parent — reduce to naming an id rather than describing a position, and the convergence argument from the pure-function view goes through unchanged.
