Composing CRDTs

Everything so far has been a primitive CRDT — a counter, register, list, or text solving one specific problem. Real applications combine several, which raises the question of how to build something complex without losing the guarantees established earlier. The answer leans on the definition: a CRDT's semantics are a pure function over the operation history, and if you compose two CRDTs properly the result is still such a pure function, so it is still a valid CRDT. The guarantee comes for free.

Composition has two concrete advantages over writing a CRDT from scratch:

  • Semantically, you are guaranteed the composed output is actually a CRDT
  • Algorithmically, you get op-based and state-based algorithms "for free," inherited from the components

Storage Versus View

Take a string h e l l o rendered as a linked list. The composition splits into two layers. The storage layer is the CRDT — characters carrying stable, immutable positions. The view layer is what builds the linked list at runtime: once all operations have been applied and the sequence of characters has converged, you walk that stable sequence and construct whatever representation the app actually needs. The CRDT never knows about linked lists; it only guarantees a converged sequence for the view to read.

UI = f(state)

This is the same move React made, one layer down. Before React you wrote JavaScript by grabbing DOM nodes and mutating them directly:

document.getElementById("name").innerHTML = "Alice";

DOM state then lived smeared across dozens of places, mutated by different events at different times, and it became genuinely hard to reason about what the UI should look like for a given application state — because the UI was the result of a sequence of mutations rather than a reflection of a known state. React stopped thinking about mutations and thought about state: UI = f(state). You update the state, React derives what the DOM should be, and you never touch the DOM directly.

The pre-React problem is the distributed-systems problem. Multiple clients directly mutating shared state produce the same inconsistencies that multiple events mutating the DOM did. CRDTs made React's move at a different layer: no node mutates state directly, and "state is a pure function of the operation history." The view layer then closes the loop, so the displayed state is a pure function of the CRDT state, which is itself a pure function of the operation history:

  operation history  --->  CRDT state  --->  app view
            (each arrow is a pure function)

Object Composition

The general construction is object composition: wrap several CRDTs behind a single API. The components sit side by side and do not affect each other's state; you just need to give each one a distinct name so their operations can be told apart. An ingredient row, for instance, might pair a text CRDT for the label with two LWW registers for the amount and unit:

  | olive oil  | 15  | mL |
    text CRDT    LWW   LWW

There are two equivalent ways to picture the result. One is a literal CRDT object — a class whose instance fields are its component CRDTs:

class IngredientCRDT extends CRDTObject { ... }

The other is a JSON object mapping component names to component states. Either way the objects nest arbitrarily, which is what lets composition scale up into layered, object-oriented architectures or, equivalently, JSON-like trees.

Notes

The chain history → CRDT state → view is the whole survey in one line: each arrow is a pure function, and purity at every hop is exactly what buys both convergence across replicas and predictability in the UI. CRDTs and React turn out to be the same idea aimed at different layers of the stack.
