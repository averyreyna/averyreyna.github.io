Higher-Order Functions: allp and filterAll

Exercise 2.3 from A Quarter of Haskell. The task is to write allp, which asks whether a value satisfies every predicate in a list, and filterAll, which keeps the values that satisfy all of them.

divisibleBy :: Integral n => n -> n -> Bool
divisibleBy d n = (n `mod` d) == 0

allp :: [a -> Bool] -> a -> Bool
allp ps x = and [ p x | p <- ps ]

filterAll :: [a -> Bool] -> [a] -> [a]
filterAll ps xs = filter (allp ps) xs

filter is not something I wrote; it comes from the Prelude. I only wrote allp and filterAll.

Partial Application

divisibleBy needs two arguments before any Bool exists, so divisibleBy 2 is not a Bool. It is a function still waiting for a number. I had assumed that applying a function always had to produce a result, which is why I expected [divisibleBy 2, divisibleBy 3] to be a list of Bools. It is a list of functions, with type [a -> Bool]. Correcting that one assumption is what unlocked the rest of the exercise.

divisibleBy 2     :: Integral n => n -> Bool   -- a function still waiting for a number
divisibleBy 2 6   :: Bool                       -- now it is a Bool (True)

Predicates as a Checklist

A predicate is just a function returning Bool, which is to say a yes/no question, and a list of predicates is a checklist. allp collapses a single value against the whole checklist by and-ing the answers together. && compares two things, and and does the same across a list of any length, so allp ps x = and [ p x | p <- ps ] reads as "apply every predicate to x and combine the answers with and." The comprehension distributes the single x to each predicate in turn.

Deriving It by Generalizing

allp is the two-predicate case written out and then generalized:

p1 x && p2 x                    -- hardcoded for exactly two predicates
= and [ p1 x, p2 x ]            -- "&&" across a list is what `and` does
= and [ p x | p <- [p1, p2] ]   -- the comprehension is shorthand for that list
= and [ p x | p <- ps ]         -- let the list be any ps; this is allp's body

filterAll is then filter (allp ps). Here allp ps is partial application again: it is a single predicate, which is exactly what filter expects. filter does the work of walking the list, while allp collapses one value to a verdict.

Notes

Why it is safe to put functions in a list at all comes down to referential transparency. A pure function returns the same output for the same input and has no side effects, so a list of them carries no hidden state. The larger shift is that you write an equation saying what the answer is rather than the steps to compute it. allp ps x = and [ p x | p <- ps ] is a definition, not a loop, with no iteration and no mutable state, and the type [a -> Bool] -> a -> Bool tells most of the story before you read the body. This connects back to the lambda calculus, where functions are first-class values, and to the functor view of map.

One method worth keeping: when the explanations stopped helping, what worked was closing the prose, opening GHCi, and going one line at a time, predicting each result before running it. Start from something that already works, like divisibleBy 2 6, hardcode everything first, and generalize last. The rename from concrete values to variables is how the general function gets born.
