CRDT Semantics as a Pure Function

Part 2 of the survey reframes everything from the introduction around a single idea: CRDT semantics are a pure function of the operation history. The function maps the history of operations users have performed to the current app-visible state, and like any pure function it is deterministic and side-effect free — the same input always produces the same output.

  operation history
  [+1  +1]
  [+1  +1]  ---->  pure function  ---->  app state (6)
  [+1  +1]

The operation history is a set, and that is the load-bearing word. Because sets are unordered, the function must produce the same result regardless of the order in which operations happen to arrive across different nodes. In the functional-programming sense this purity is not just about correctness — it is specifically about convergence. Every replica runs the same algorithm over the same set and is therefore guaranteed to reach the same state.

The Three Components

Concretely, a CRDT's semantics consist of three pieces:

  • A collection of operations users are allowed to perform on the CRDT (for example, calling inc())
  • For each operation, a translated version that gets stored in the abstract operation history — the index-based "delete the item at index 0" becomes something tombstone-aware that names what was deleted
  • A pure function that inputs a set of translated operations plus some ordering metadata and outputs the intended state of a user who is aware of those operations

It helps to picture the history as a git commit graph. The "ordering metadata" is the collection of arrows indicating which operations were aware of which others. The translation and pure-function steps are equal in importance: translation stabilizes the input so the function has something order-independent to work on.

Unique ids are the connector that makes translation possible, because they are what render a translated operation context-independent. "Delete at index 0" is a context-dependent instruction whose meaning shifts depending on what else has run; "delete the element with this id" means the same thing even under concurrency. The ids are load-bearing on purpose.

Causal Order

The arrows in those history diagrams are the causal order, the partial order ≺ on pairs of operations defined by two rules:

  • If a user had received operation o before performing their own operation p, then o ≺ p — this includes the case where one user performed both o and p in that order
  • Transitivity: if o ≺ p and p ≺ q, then o ≺ q

The vocabulary that comes off of this is worth pinning down. When o ≺ p we say o is causally prior to p, that o is a causal predecessor of p, and that p is causally greater than o; equivalently, "o happened before p" or "p is causally aware of o." When neither o ≺ p nor p ≺ o holds, o and p are concurrent. Finally, o is an immediate causal predecessor of p iff o ≺ p and there is no r with o ≺ r ≺ p.

  A ---> B
          \
           v
           D ---> C

Reading the diagram: B is causally greater than A, B is causally prior to C, and B is concurrent to D. The immediate causal predecessors of C are B and D; A is a causal predecessor of C but not an immediate one, since its relationship is implied by transitivity. These immediate predecessors are exactly the pairs connected by an arrow — every non-immediate predecessor is left implicit.

This is why a CRDT can track the causal order cheaply: label each operation with the ids of its immediate causal predecessors, the tails of its incoming arrows, and the rest follows by transitivity. Many CRDT-based apps go further and enforce causal-order delivery — a replica will not process an operation, or update the app state, until it has processed every causally-prior operation first. If B causally depends on A, then A is always delivered before B on every node.

Notes

The basic techniques here come straight out of database and programming folklore; the survey's contribution is naming them as semantic techniques — building blocks you reach for when deciding what concurrent edits should mean, not just how to replicate them efficiently.
